# Данные и хранение

Всё хранится на устройстве. Своего сервера у Melete нет; данные покидают устройство, только когда человек сам
это делает: резервная копия, папка Melete, файл команде, синхронизация с компьютером.

## Два хранилища и почему два

| | localStorage | IndexedDB |
|---|---|---|
| Что | состояние: песни, занятия, события, настройки | файлы: записи, видео, табы, PDF, MIDI, модули Библии; проекты студии и лупера; куски идущей записи; копии на устройстве |
| Как пишется | синхронно, целиком, сразу | асинхронно, по записи |
| Почему так | переживает вылет приложения в любой момент; простая модель «прочитал — изменил — сохранил» | файлы большие (до сотен МБ), в localStorage не помещаются (5–10 МБ на сайт) |

## Состояние: `practice.v1`

Модуль — `src/core/store.js`. Формат совместим с прототипом (`legacy/practice.html`): ключ `practice.v1`,
поле `version: 1`. Совместимость с данными прошлых версий проверяет `tests/compat.test.js`.

```js
{
  version: 1,
  songs:    [{ id, title, artist, genre, cat, tags, key, targetBpm, currentBpm, notes /* текст с аккордами */,
               difficulty, masteryPct, createdAt, updatedAt, deleted? }],
  sessions: [{ id, type: 'free'|'song'|'tool', songId, tool, start, end, dur /* с */, bpm, mode, quiet?, study?,
               tag, note, clk?, sig /* печать */, updatedAt, deleted? }],
  events:   [...],   // календарь (core/calendar.js), появляется с первым событием
  projects: [...],   // проекты студии (music/project.js) — в памяти здесь же, на диске — в своей базе (ниже)
  schema,            // номер формата (core/migrate.js), version не меняется
  settings: { goalMin, days, plan, remind, theme, lang, profile, lib, cal, bible, metro, ..., updatedAt },
  updatedAt
}
```

API хранилища (`createStore`): `state` — живой объект; правка — прямо в объекте, затем `save()` (ставит `updatedAt`,
пишет, оповещает подписчиков) или `persist()` (пишет без смены `updatedAt` — для частых мелочей вроде темпа метронома).
`settingsChanged()` — то же для настроек. Экраны подписаны через `subscribe(fn)`.

**Битые данные не затираются.** Если JSON при запуске не читается, исходная строка откладывается в
`practice.v1.broken` до того, как приложение что-либо запишет; дальше оно работает с пустого состояния.
**Нет места** — `onWriteFail`: запись в журнал и сообщение «Освободить место» (не чаще раза в минуту).

### Удаление и слияние

Песни, занятия и события **не стираются**, а помечаются `deleted: true`: так удаление переносится копиями и
синхронизацией, а время удалённой песни остаётся в статистике.

Слияние двух состояний (`store.js: merge`, `backupparts.js`) — одно правило на всё: **по `id` побеждает запись
с бóльшим `updatedAt`**. Ничего не теряется: чего нет в одной стороне, берётся из другой. На этом правиле стоят
загрузка резервной копии, папка Melete и синхронизация телефона с компьютером.

### Настройки: общие и этого устройства

- `settings` в `practice.v1` — то, что принадлежит человеку и переезжает с ним: цель недели, расписание,
  напоминания, профиль, оформление, метки песен (`core/settings.js`).
- `practice.v1.tools` — то, что принадлежит устройству: микшер, звук пианино, пэды, строй тюнера, раскладки окон,
  настройки каждого инструмента (`core/device.js`; модули читают и пишут свой кусок через `ctx`).
  Синхронизацией не переносится (у телефона и компьютера разные динамики и экраны).

### Занятия и печать

Идущее занятие — отдельный ключ `practice.v1.active` (`core/session.js: createActive`): отрезки пауз и «вдали»,
время по темпам, признаки игры. Оно переживает перезагрузку и погашенный экран. При завершении `buildRecord`
строит запись, `store.addSession` ставит **печать** (`core/integrity.js: seal`): хеш полей
`id|type|songId|tool|start|end|dur|mode|quiet|src|clk`. Заметку и метку менять можно — их печать не касается.

Статистика, неделя и самоцвет (`stats.js`, `mastery.js`) берут только записи с верной печатью
(`store.sessions()`); неподтверждённые видны лишь в истории (`store.unverified()`). Не подтверждаются: правка записи
в файле копии, записи при сбитых часах (`core/clock.js`), невозможные (раньше 2025 года, в будущем, длительность больше отрезка `start–end`; за одни сутки больше
24 часов — тогда весь день).
Это не защита от взлома, а честная статистика: человеку незачем «рисовать» часы.

**Нельзя** менять запечатанные поля у существующих записей — запись перестанет считаться. Новое поле, которое
может меняться, кладите вне списка печати (как `study`).

### Расписание и прежние поля

`settings.plan` (`core/schedule.js`) — блоки занятий по дням недели, перерывы по датам, правки одного дня. Прежние
поля `days`, `remind.time`, `remind.dayTimes`, `goalMin` расписание заполняет само (`savePlan → legacyOf`): напоминания,
главная и статистика читают их, как раньше. Так новая функция не ломает старый код и старые копии.

### Проекты студии — в своей базе (с 12.11.2026)

Проекты студии и петли лупера с нотами — самые большие и самые «горячие» данные: меняются на каждую правку ноты.
Раньше каждая правка переписывала всё `practice.v1` синхронно (20–100 мс и квота localStorage 5–10 МБ на сайт).
Теперь они лежат в IndexedDB `melete-proj` (`core/projstore.js`), а `store.js` пишет туда **только изменённый проект**.

Для модулей ничего не поменялось: `state.projects` — живой список в памяти, правка — через `ctx.projects.save(p)`
(он отмечает проект `store.projectChanged(id)`, и правка в ту же миллисекунду тоже доходит). В копию, синхронизацию
и папку проекты попадают как раньше — из памяти. Режимы `store.projMode`:

- `wait` — первые миллисекунды после запуска, база читается; `practice.v1` пишется как раньше, с проектами;
  модули ждут `store.ready` (`modules.js`), копии на устройстве — тоже (`snapshots.js`).
- `side` — проекты в базе, в `practice.v1` их нет.
- `ls` — базы нет (приватный режим, тесты) или она отказала: проекты в `practice.v1`, как раньше.

**Переход безопасен при обрыве**: проекты из `practice.v1` сначала записываются в базу (ответ — после записи
транзакции), и только потом убираются из `practice.v1`. Проекты в `practice.v1` при запуске (старый формат или
правки, сделанные откатанной сборкой) сливаются с базой по `updatedAt` и переезжают. **Отказ базы при записи** —
режим `ls`: проекты сразу возвращаются в `practice.v1`, человеку — «Освободить место» (`onWriteFail`).
«Удалить все данные» очищает и базу. Откат на сборку до 12.11.2026 проектов не видит (они в базе), но и не теряет:
новая сборка их найдёт.

## Файлы: IndexedDB `practice-audio`

Модуль — `src/core/files.js`, хранилище `tracks` (имя — как в прототипе). Запись файла:

```js
{ id, name, size, type, blob, created, songs: [songId…], kind?: 'audio'|'tab'|'midi'|'bible'|'daw',
  dur?, peaks? /* волна */, video?,
  ana?  /* тональность, темп, доли, аккорды — разбор записи */, lyr? /* текст песни */,
  stem? /* дорожка: { src, part, mode, db } */, trans? /* ноты из записи */, fmt?, variant? }
```

Все записи держатся в памяти списком (`files.list(kind)`, `files.get(id)`), `blob` — ссылка на данные в базе.
`add(rec)` возвращает `false`, если файл не лёг в базу; нет места — `onWriteFail` и пометка `unsaved`; прочие ошибки —
`onError` в журнал. Базы нет совсем (приватный режим) — `files.noDb`, файлы живут до закрытия.

Результаты обработок (дорожки, ноты, очищенная запись) — **новые файлы рядом** с исходником, с пометкой, откуда они
(`stem.src`, `trans.src`, `dn.src`). Исходник никогда не перезаписывается.

Известный долг (разбор `docs/archive/audit-2026-11.md`): правка трёх полей разбора (`ana`) переписывает запись
вместе с blob. Отдельное хранилище сведений — будущая схема базы v2.

## Резервная копия

`core/backup.js` + `core/backupparts.js`. Копия — тот же JSON `practice.v1` с подписью `backupInfo: { by, at, app }`
и по желанию с файлами (`files: [{ ...запись, data: base64 }]`). Части по выбору: настройки, песни (с файлами),
профиль и статистика, план чтения, календарь. Загрузка **ничего не удаляет** — только слияние.

Куда: папка Melete (`Data/Backups`), иначе «Поделиться» (Android) или скачивание. Копия с файлами собирается
в памяти целиком (файл → base64 → JSON, примерно вчетверо больше), поэтому у файлов потолок: телефон 24 МБ,
компьютер 160 МБ (`FILES_LIMIT`), свежие — первыми; все файлы целиком хранит папка Melete.

Страховки без участия человека: копии на устройстве раз в сутки и перед обновлением (`snapshots.js`), автокопия
в папку Melete раз в неделю с архивом по месяцам (`folder.js`).

## Папка Melete

`core/folder.js` (логика, без DOM) + `core/foldersync.js` (когда синхронизировать). Человек выбирает папку
(Android — SAF через `FolderPlugin.java`; компьютер — обычная папка, `desktop.js`), приложение раскладывает:
`Data/` (копия данных и копии с подписью), `Media/`, `Tabs/`, `PDF/`, `Lyrics/` (тексты песен файлами `.cho`).

Медиатека и папка — **зеркало в обе стороны**: новое в одной стороне появляется в другой, удалённое — удаляется.
Защита от потери: если с одной стороны пропало сразу много файлов **или все** (вынута карта, отозван доступ,
база не прочиталась), ничего не удаляется, только запись в журнал (`out.held`). Тексты песен сверяются по хешу и
времени правки файла.

## Миграции

Шаги формата — один список `core/migrate.js: STEPS` (с 12.11.2026). `version` остаётся `1` навсегда: по нему старые
версии и прототип узнают свои данные и копии. Номер формата — отдельное поле `schema` = число шагов, которые знает код.

- Шаг — `(state) → true`, если что-то поменял; **обязан быть идемпотентным**: шаги идут при запуске, после загрузки
  копии и после синхронизации (`store.js: runMigrate` в `createStore`, `importBackup`, `replaceState`) — данные со
  старого устройства приходят в старом виде.
- Шаг поменял данные — `settings.updatedAt` сдвигается, состояние сохраняется сразу.
- Данные новее кода (`schema` больше: откат сборки) — шаги идут, `schema` не понижается (и слиянием тоже),
  в журнал — предупреждение. Битые данные при запуске — шаги не идут.
- Сломанный шаг не роняет запуск: ошибка — в журнал, остальные шаги идут.
- Правило прежнее: новое поле — необязательное, с умолчанием при чтении; старое поле не удаляется, пока его читает
  старый код или старые копии. Новый шаг — в конец списка; несовместимая правка — ещё слепок в `tests/fixtures`.

Настройки устройства (`device.js` — поля прототипа) приводятся при запуске, как раньше. Тесты — `tests/datastore.test.js`.
