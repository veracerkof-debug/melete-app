### 🔴 Критично

#### 1. Сломанное хранилище на телефоне стирает медиатеку компьютера

`src/core/sync.js:388-392`, `src/core/files.js:42`

Если IndexedDB на телефоне не открылась, `files.noDb = true`, а список файлов пуст.
Телефон отправляет компьютеру **пустой манифест**. Компьютер сравнивает его со своим
списком и с множеством «последней синхронизации» — получается, что все файлы удалены:

```js
const mine = manifestOf(allFiles(F)), plan = planFiles(mine, r.files || [], pc.ids || []);
// plan.delTheirs = все файлы компьютера, которых нет в пустом манифесте телефона
if (plan.delTheirs.length) await call('POST', '/melete/v1/delete', { json: { ids: plan.delTheirs } });
```

Сервер (`src/core/sync.js:157-161`) удаляет без всяких проверок. Итог: **у компьютера
исчезает вся медиатека, потому что на телефоне сломался индекс или кончилось место.**

Тот же класс проблем в зеркале папки **закрыт** — `src/core/foldersync.js:55` подставляет
`removeFile: null`, когда `app.files.noDb`. В `sync.js` такой проверки нет.

**Как исправить**

```js
// src/core/sync.js, перед расчётом плана
const broken = !!app.files?.noDb;
const plan = planFiles(mine, theirs, pc.ids || []);
if (broken) {
  plan.delMine.length = 0;    // свои удаления не считаем — база не читается
  plan.delTheirs.length = 0;  // чужие удаления тоже: список у нас пуст, а не «удалено всё»
}
```

Плюс на сервере: `/melete/v1/delete` отклонять, если в запросе больше половины
известных серверу файлов (или если клиент прислал флаг «у меня база недоступна»).
И третьим слоем — требовать от клиента явного подтверждения удаления: сейчас удаление
выводится из молчаливого отсутствия файла в манифесте.

#### 2. Зеркало папки при 1–3 файлах по-прежнему удаляет записи из медиатеки

`src/core/folder.js:134`

```js
const mapped0 = Object.keys(mem.files).length,
      risky = (n, empty) => n > 0 && (empty || (n > 3 && n > mapped0 / 2));
```

Предложение из прошлого разбора (`n === mapped0 || n > mapped0 / 3`) **не применено** —
защита «пустая сторона» добавлена, но порог `n > 3` остался.

Сценарий: у человека 2 записи в `Melete/Media/` и 1 табулатура в `Melete/Tabs/`.
Папка временно читается не полностью (отозван доступ SAF к подпапке, папка переехала,
сбой чтения). `dirEmpty` ложно — в `Tabs` файл есть. `goneDir.length = 2` → `2 > 3` ложно →
**две записи удаляются из медиатеки без спроса.** Ровно тот класс, который прошлый разбор
описал и который до сих пор не закрыт.

**Как исправить**

```js
const risky = (n) => n > 0 && (n === mapped0 || n > mapped0 / 3);
```

Плюс отдельная проверка: если `ls` для отслеживаемой папки пуст, но раньше там были
файлы, — считать это «недоступно» и не удалять ничего (сейчас это сделано только для
«пустой стороны целиком»).

#### 3. Утечка: «Камень» и «камни лиг» не снимают слушатель с `document`

`src/ui/stone.js:333`, `src/ui/gem3d.js:558`

```js
document.addEventListener('visibilitychange', () => { if (document.visibilityState === 'visible') kick(); else saveQ(key, q); });
```

Слушатель снимается **никогда**. `stoneView()` и `gemView()` не возвращают функцию
отписки, а `mountStones` (`src/core/screens/home.js:359`) вызывается при каждой
перерисовке главного экрана (`src/core/screens/shell.js:103`).

Измерено на живом сайте — 10 циклов «открыть метроном → закрыть»:

| | слушателей `document.visibilitychange` |
|---|---|
| после загрузки | 13 |
| 2 цикла | 17 |
| 4 цикла | 21 |
| 6 циклов | 25 |
| 8 циклов | 29 |
| 10 циклов | 33 |

**Ровно +2 за цикл, линейно, без очистки** (один камень + один камень лиги). Каждый
слушатель удерживает замыкание с холстом и 3D-мешем — память растёт вместе с числом
перерисовок. Правило проекта «таймер без остановки — дефект» здесь нарушено в самом
заметном месте.

**Как исправить**

```js
// src/ui/stone.js — вернуть отписку
return {
  setHours(h) { ... },
  redraw: draw,
  destroy() {
    document.removeEventListener('visibilitychange', onVis);
    if (raf) cancelAnimationFrame(raf);
  },
};
```
и в `home.js: mountStones` — перед перерисовкой снимать старые:
```js
root._stones?.forEach((s) => s.destroy());
root._stones = [...];
```
Альтернатива дешевле: **один** слушатель `visibilitychange` на уровне приложения
(`src/core/index.js`), который обходит зарегистрированные камни.

#### 4. `stop()` при исключении оставляет микрофон открытым

`src/core/recorder.js:258-269`

```js
r.mr.onstop = async () => { teardown(); ... };
try { r.mr.stop(); } catch { done(null); }   // ← teardown() не вызван
```

`teardown()` — единственное место, где закрывается микрофон и останавливается таймер
уровня (20 мс). Если `mr.stop()` бросит исключение (состояние `inactive`, гонка с
переключением вкладки, разрыв соединения), микрофон **остаётся открытым до
перезапуска приложения**, а куски записи — на диске.

**Как исправить**: вынести освобождение из `onstop` и вызвать в обоих путях:

```js
const release = () => { teardown(); if (r.video) r.video.stop(); };
r.mr.onstop = async () => { release(); ... };
try { r.mr.stop(); } catch { release(); r.take.drop?.(); done(null); }
```
Дополнительно: `teardown()` стоит вызывать и в `disarm()`/при `visibilitychange` —
сейчас лист закрыли во время запроса разрешения — починено, а вот при уходе в фон
микрофон остаётся.

#### 5. `saveMidi` сообщает об успехе, когда файл не записался

`src/core/recorder.js:166-173`

```js
try { await app.files.add(rec); return rec; } catch { return null; }
```

`files.add()` при нехватке места **не бросает исключение, а возвращает `false`**
(`src/core/files.js:52`). Значит `saveMidi` возвращает запись, пользователю показывают
«take сохранён», а в базе его нет — файл исчезает при перезапуске.

**Как исправить** — как в `saveTake`:
```js
try { if ((await app.files.add(rec)) === false) throw new Error('нет места'); return rec; }
catch (e) { log('rec', 'MIDI-запись не сохранилась: ' + (e && e.message), 'e'); return null; }
```

#### 6. `files.add` не заменяет запись с тем же id → дубли и «призраки»

`src/core/files.js:48-53`

```js
async add(rec) {
  all.push(rec);      // ← без проверки: тот же id уже есть?
  emit();
  try { await tx('readwrite', (st) => st.put(clean(rec))); return true; }
```

`st.put` перезаписывает запись по `keyPath: 'id'`, а вот `all` — массив в памяти —
получает **дубль**. Сценарий: запись сохранена в медиатеку, но `spool.drop(id)` не
успела (сбой) → при следующем запуске `recorder.recover()` (`src/core/recorder.js:197`)
склеивает её заново и сохраняет под тем же id. В IndexedDB запись одна, а в `all` — две.
`files.get(id)` возвращает **первую** (старую, без свежего разбора), `files.remove(id)`
удаляет только одну — после перезапуска файл «воскресает».

**Как исправить**
```js
async add(rec) {
  const i = all.findIndex((r) => r.id === rec.id);
  if (i >= 0) all[i] = rec; else all.push(rec);
  emit();
  ...
}
```

### 🟠 Высокий

#### 7. Копия на компьютере собирается целиком в памяти

`src/core/backup.js:61-77`. Потолок для десктопа — 160 МБ (`FILES_LIMIT`).
`toB64` → `blob.arrayBuffer()` → строка (+⅓) → `JSON.stringify` (ещё одна копия) —
итого **≈ 600–700 МБ живых строк**, и всё это на главном потоке. На 8 ГБ машине это
граница OOM, на телефоне — мгновенная выгрузка процесса. Комментарий в коде признаёт
проблему, но решение ограничило только телефон (24 МБ).

**Как исправить**: собирать копию **потоком** — писать JSON по частям в поток/файл
(`WritableStream` + `TextEncoder`), не держать весь результат строкой; base64 — по
чанкам с переносом строк (тогда `atob` не нужен целиком); на десктопе снизить потолок
до 40–60 МБ; для файлов — отдельная часть копии (`files` + `filesIndex`), чтобы можно
было грузить по требованию.

#### 8. Перезапись blob ради трёх полей разбора

`src/core/files.js:64` (`files.save`) — вызывается из `src/core/autostems.js` и
`src/core/jobs.js`, чтобы записать `ana` (тональность/темп), `stemsAbsent`, `stemsAt`.
Запись переписывается целиком, вместе со звуковым blob: 20 МБ ради трёх полей.
Известная находка A7 — **не исправлена**.

**Как исправить**: отдельный магазин метаданных (`IndexedDB` v2, стор `meta`),
`files.save` → `files.setMeta(id, patch)`. Требует миграции — см. п. 11.

#### 9. Нет миграций схемы IndexedDB

`src/core/files.js:21` (`indexedDB.open(DB, 1)`), `src/core/recspool.js:13`.
`onupgradeneeded` создаёт сторы, но **механизма `version → migrate` не существует**:
любое изменение формата записи = полная потеря доступа к данным, без предупреждения.
Это известная находка D3 — не исправлена.

Дополнительно: **не обрабатывается `r.onblocked`** → если база открыта в другой вкладке,
`open()` не сработает никогда, промис зависнет, и `recspool.blob()`
(`while (pending.size) await Promise.all(...)`) будет крутиться вечно — кнопка «Стоп»
перестанет отвечать.

**Как исправить**
```js
const r = indexedDB.open(DB, 2);
r.onupgradeneeded = (e) => {
  const d = r.result, tx = r.transaction;
  if (e.oldVersion < 1) d.createObjectStore(STORE, { keyPath: 'id' });
  if (e.oldVersion < 2) { const m = d.createObjectStore('meta', { keyPath: 'id' }); /* перенос */ }
};
r.onblocked = () => onError('open', new Error('база занята другой вкладкой'), null);
```

#### 10. Всё состояние — один ключ localStorage, пишется целиком и синхронно

`src/core/store.js:105-107`:
```js
const write = () => { try { storage && storage.setItem(LS, JSON.stringify(state)); } catch (e) { onWriteFail(e); } };
```

Каждое сохранение сериализует **всё** состояние: все проекты студии с массивами нот,
все сессии за два года, все настройки. `persist()` (частые правки метронома) — тот же
полный снимок. Отсюда фриз в такте на 1–3 МБ состояния и тихая потеря правки при
переполнении квоты (`onWriteFail` — только «нет места»). Известная находка A2 — **не
исправлена**.

**Как исправить (по шагам, чтобы не сломать совместимость)**
1. Ввести `version: 2` в формате состояния и `migrate(state)` — `store.js:33`.
2. Разделить на «горячие» (настройки, последняя сессия) и «холодные» (история, проекты
   студии) — например `practice.v2.hot` / `practice.v2.songs` / `practice.v2.sessions`.
3. Историю и проекты студии писать в IndexedDB, а не в localStorage (квоты localStorage
   — 5–10 МБ, IndexedDB — гигабайты).
4. Запись в горячую часть — `requestIdleCallback`/дебаунс 300 мс; в холодную — сразу.

#### 11. Синхронизация затирает настройки без сравнения `updatedAt`

`src/core/backupparts.js:68`
```js
if (on.has('settings')) Object.keys(P).forEach((k) => { if (!OWNED.has(k) && !LOCAL.has(k)) S[k] = clone(P[k]); });
```
Ключи настроек копируются из чужих данных **безусловно**. Тогда как `store.merge`
(`src/core/store.js:59`) выбирает настройки по `settings.updatedAt`. Расхождение:
телефон со сброшенными настройками при синке вернёт компьютеру дефолты (`goalMin: 300`,
тему по умолчанию) вместо его собственных.

**Как исправить**: в `applyParts` для `settings` применять то же правило, что и в
`merge`: брать настройки целиком у того, у кого `settings.updatedAt` больше, либо
сравнивать по ключам.

### 🟡 Средний

#### 13. Восстановление копии не атомарно
`src/core/backup.js:80-98` — состояние заменяется целиком, затем добавляются файлы.
Сбой на середине → состояние новое, файлы добавлены частично. Нужен промежуточный
этап: собрать всё в памяти, записать в базу, и только потом `replaceState`.

#### 14. Файлы сверх потолка молча не попадают в копию
`src/core/backup.js:41-49, 69` — только запись в журнал и `report.skipped`. Человек
может месяцами считать, что у него копия, а половины записей в ней нет. Показывать
предупреждение до сохранения (не только после) и в самой копии — поле
`filesSkipped`, чтобы при восстановлении человек знал.

#### 15. `recspool` при отказе диска держит всю запись в памяти молча
`src/core/recspool.js:72` — `.catch(() => { mem.set(n, blob); })`. Кончилось место →
вся запись уходит в RAM: ровно тот сценарий, ради которого куски пишутся на диск.
Нужно логировать, предупреждать и останавливать запись (или сжимать).

#### 16. Веб-версия тянет 21 МБ модели терменвокса молча
`mediapipe/` в сборке — `hand_landmarker.task` 7.6 МБ + wasm 12.7 МБ. Пользователь
мобильного интернета получает 20 МБ без предупреждения. По образцу существующих
«пакетов» (`build/packs.json`, `src/core/packs.js`) модель должна уезжать по кнопке,
с размером и прогрессом. Известная находка C1 — не исправлена.

#### 17. Сборка: весь вес грузится сразу, ленивой загрузки нет
Живая `/show/`: 61 ресурс, **1.75 МБ сырых / 630 КБ по сети**, и **все 18 `meta-*.js`
в `modulepreload`** — браузер тянет их до того, как приложение интерактивно.
`main-*.js` — 642 КБ сырых (230 КБ по сети), `main.css` — 128 КБ (26 КБ по сети).

**Как исправить**: `manualChunks`/`dynamic import` для модулей, которые открывают раз в
неделю (статистика, отчёт, календарь, диагностика, справка) — это уже отдельные
чанки `stats-*.js`, `report`… Простой шаг: убрать `modulepreload` для редко
используемых чанков (сделать их `import()` по требованию) — сеть станет легче втрое.

#### 18. CSP в проде разрешает WebSocket на любой хост
`index.html`: `connect-src 'self' blob: data: https://musicbrainz.org https://api.github.com ws://localhost:* ws://*:5173`.
`ws://*:5173` — это **любой** хост на порту 5173, в том числе в локальной сети.
В продакшен-странице это лишнее (нужен только `ws://localhost:*` для `vite` в
разработке). Плюс нет `Permissions-Policy`, `frame-ancestors`, `strict-dynamic`.

**Как исправить**: развести CSP для разработки и продакшена (`transformIndexHtml` по
`mode`), в проде оставить `connect-src 'self' blob: data: https://musicbrainz.org https://api.github.com`,
добавить `frame-ancestors 'none'` и `Permissions-Policy: microphone=(self), camera=(self)`.

#### 19. `android:usesCleartextTraffic="true"`
`android/app/src/main/AndroidManifest.xml` — обычный HTTP разрешён во всех сценариях,
включая мост «Melete DEV» с TLS. Для приложения, которое соединяет два устройства по
сети, стоит ограничиться HTTPS/TLS или явно описать, где это допустимо.

#### 20. `REQUEST_INSTALL_PACKAGES` в манифесте
Тот же файл. Комментарий в коде: «в сборке для Google Play — убрать». Пока сборка
идёт через GitHub — осознанно, но стоит вынести в отдельный `manifest` для Play, иначе
политика Google отклонит пакет.

#### 21. Демо-страница делит origin с настоящим приложением
`src/showcase/ns.js` патчит `Storage.prototype` **глобально** и `indexedDB.open`.
Разделение данных работает (префикс `melete-show:`), но:
- патч глобальный — любой сторонний скрипт на этой странице тоже получит префикс;
- **`localStorage.clear()` не пропатчен** — сброс данных в демо снёс бы данные
  настоящего приложения на том же origin;
- `src/core/cleanup.js:17` чистит ключи по префиксу `practice.` — в демо ключи
  называются `melete-show:practice.*`, чистка их не видит (мелочь, но демо будет
  копить мусор);
- `indexedDB.open` пропатчен по имени — а вот `indexedDB.deleteDatabase` тоже, хорошо.

**Как исправить**: патчить не `Storage.prototype`, а конкретный экземпляр
(`localStorage.setItem = ...` на объекте), и добавить пропатченный `clear()`,
удаляющий только свои ключи.

#### 22. Посев демо неустойчив к сбою
`src/showcase/main.js:135`
```js
seed(app).finally(() => { localStorage.setItem(DONE, '1'); location.reload(); });
```
Если посев упал на середине, флаг всё равно ставится — **демо остаётся наполовину пустым
навсегда**, повторного посева не будет. Плюс `location.reload()` теряет позицию
пользователя.

**Как исправить**: ставить `DONE` только после успеха (`seed(app).then(() => setItem(...))`),
при ошибке — показывать тост и не ставить флаг; перезагрузку делать через
`location.replace` и только на первом заходе.

#### 23. Демо: длительность занятия инструментом не сходится с `end − start`
`src/showcase/main.js:68, 81` — для `type: 'tool'` `dur` обрезается до 40 минут, а `end`
считается по полной длине. В истории и в статистике одно и то же занятие выглядит
по-разному.

#### 24. 136 пустых `catch` — ошибки глотаются
По всему `src/`. Критичные места, где теряются данные:
`src/launcher/money-page.js:79` и `src/launcher/notes-page.js:25` — запись в
localStorage без проверки квоты: при переполнении данные исчезают молча.
`src/core/cleanup.js` — снос старого без записи в журнал.

**Как исправить**: правило «пустой catch — только для ответа пользователю или в журнал»,
как уже сделано в `files.js` (`onError`).

#### 25. `localStorage.setItem` без проверки квоты в горячих путях
`src/core/store.js:107` — при переполнении `write()` зовёт `onWriteFail`, и состояние
теряется целиком. См. п. 10 (разделение данных) — это же его следствие.

#### 26. `cleanup.js` чистит по префиксу `practice.` — демо и реальное приложение делят правило
`src/core/cleanup.js:17` — в демо ключи с префиксом `melete-show:` под правило не
попадают, чистка там не работает. Мелочь, но при смене схемы хранения правило надо
перенести в общий слой.

#### 32. `JSON.stringify(state, null, 1)` в экспорте копии

время на главном потоке. Для машинного формата лучше без отступов, для «человеческой»
копии — дамп отдельной кнопкой.
