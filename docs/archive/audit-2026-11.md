## Осталось (ждёт решения автора)

**A2. Горячие и холодные данные.** `src/core/store.js:105-107` — каждое сохранение
пишет **всё** состояние целиком и синхронно (`JSON.stringify` → `setItem`). В состоянии
все проекты студии с массивами нот; каждая правка ноты сохраняет всё это, а `snap(p)`
(`src/modules/studio/index.js:68`) сериализует проект ещё раз для стека отмены (до 40
копий). Отсюда: фриз 20–100 мс в такте при 1–3 МБ состояния и исчерпание квоты
localStorage (5–10 МБ) → правка потеряна. Разделение данных затрагивает совместимость
старых копий и синхронизацию — решение за автором.

**A7. Перезапись blob.** `files.save(r)` пишет запись целиком, вместе со звуковым
blob, ради трёх полей разбора (`ana`, `stemsAbsent`, `stemsAt`): `src/core/autostems.js:91`,
`src/core/jobs.js:71`. Чтобы не переписывать 20 МБ, нужен отдельный магазин метаданных —
это схема IndexedDB v2 и миграция старых записей.

**D3. Миграции схемы.** `src/core/store.js` держит `version: 1`, миграций в коде нет.
`tests/compat.test.js` проверяет совместимость, но механизма `version → migrate(state)`
не существует. Стоит завести до того, как формат данных сдвинется.

**C1. Модель терменвокса в веб-сборке.** Веб-сборка — 48 МБ, из них `mediapipe/` 21 МБ
(`hand_landmarker.task` 7.6 МБ + `vision_wasm_internal.wasm` 12.7 МБ). Пользователь,
открывший терменвокс на мобильном интернете, получает 20 МБ молча. По образцу уже
существующих «пакетов» (`build/packs.json`, `.github/workflows/packs.yml`,
`src/core/packs.js`) модель должна уезжать по кнопке, с размером и прогрессом.

**C2. Вес главного бандла.** `main-*.js` — 647 КБ одним файлом. Кандидат на
разделение: статистика, диагностика, календарь, отчёт открываются редко.

**C3. Крупные модули.** `src/modules/audio/index.js` — 1730 строк, `panel.js` — 1028,
`theremin/index.js` — 977, `voice/index.js` — 910. Делить по образу `src/modules/studio/`

**C4. Покрытие тестами.** `studio` — 2 файла тестов, `train` — 2, `convert` — 3,

## 🔴 Зеркало папки теряет данные, когда папка временно недоступна

`src/core/folder.js:132` — `const risky = (n) => n > 3 && n > mapped0 / 2;`

Защита «пропало сразу много — ничего не удаляется» работает **только при более
чем трёх отслеживаемых файлах**. У человека с 1–3 файлами (у большинства на
старте) временно недоступная папка выглядит как «человек удалил файлы»:

- папка вернула пустой список (отозван доступ SAF, вынута карта памяти, папка
  переехала, сбой чтения) → записи удаляются **из медиатеки**;
- список записей приложения пуст (база не прочиталась) → файлы удаляются
  **из папки**.

Воспроизведено на harness из `tests/folder.test.js`: один отслеживаемый файл,
`drv.list = async () => []` → `removed: ['r1']`, `held: undefined`; в обратную
сторону — `removedDir: 1`, файл из папки удалён.

Предложение — считать подозрительным исчезновение *всех* файлов разом (человек
редко удаляет всё сразу, а недоступная папка выглядит именно так) и не удалять
из медиатеки, пока по каталогу не получен непустой список:

```js
const risky = (n) => n > 0 && (n === mapped0 || n > mapped0 / 3);
```

## 🟡 Восстановленная запись — без длительности и без волны

`src/core/recorder.js` — `recover()` вызывает `saveTake(..., 0, ...)`, а `saveTake`
пишет `dur` только если оно ненулевое. Восстановленная запись попадает в медиатеку
без длины и без `peaks`. Длительность оценивается из суммы размеров кусков и
битрейта MediaRecorder (`mr.mimeType`/битрейт известны при старте).

## 🟡 `leftovers()` собирает все куски в память разом

`src/core/recspool.js` — `leftovers()` строит Blob для каждой незакрытой записи
до возврата. Для записи в два часа это ~140 МБ в оперативной памяти телефона — тот
самый сценарий, от которого feature и защищает. `recover()` должен склеивать по
одной записи: `leftovers()` отдаёт метаданные, блок собирается в цикле.
